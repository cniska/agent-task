# agent-task Specification

> The coding-agent tasks on one machine, queued, running or in review, recorded so they can be listed in the order to start them, by project, checked against their briefs, stopped and removed.

This document states what must hold, not how. [`README.md`](README.md) has the install and a summary of every command, [`docs/commands.md`](docs/commands.md) every command, its flags and output, and the store, and [`src/README.md`](src/README.md) maps the modules that meet these requirements.

## 1. Purpose & context

Coding agents run in parallel on one machine, each on a task started from a brief, a file of instructions for that task, and the tasks still to start wait in a queue. agent-task records each task: its name, the repository the work lands in; queued, its goal, its plan, its priority, the tasks it waits after, what else it waits for and the check that says its wait is met; and, from the time it runs, the brief's path, the git blob sha of the brief's content when the work started, the session that started it and, once the work is handed back, the time it went to review.

It refuses a second task under a name it holds, refuses to start a task while one it waits after is still held, and refuses to start one while the machine is too busy for another, whatever is keeping it busy. It runs an agent's checks, its tests, checks, verifies, lints, typechecks and builds, one at a time across the machine and only while the machine is under its limits, and its plugin refuses a check an agent runs any other way. It lists the running and in-review tasks and flags one whose brief no longer has that sha or is gone or unreadable. It runs each queued task's check and lists the queued tasks in the order to start them, the ready apart from the waiting. It takes a running or in-review task back to queued when its work pauses or its review sends it back, and removes a task when its work is over, however it ended.

A task can belong to a project, added explicitly with its readable name, its repository, where the project's coordinator starts, and the directory its briefs and plans live in, so `list` can show one project's tasks alone. A project's tasks keep their own repositories.

`doctor` reports what agent-task and its plugin need in order to work, with a fix for each failure.

Before each command, agent-task tells the agent running it when a newer release is out on the channel it was installed through, naming that channel's upgrade. It asks the channel at most once a day.

`halt` stops all agent work on the machine until the owner runs `resume`. While a halt is raised, agent-task refuses to queue, start, change what a task waits for or its priority, or change a project, and the plugin refuses each session's edits, shell commands and agents, so stopping depends on no agent remembering a rule.

The `cniska-task` Claude Code plugin tells every session that queued and running work lives in agent-task. Where the session's working directory holds the brief of a running or in-review task, it adds those tasks, each with whether its brief changed.

**Primary user:** whoever runs coding-agent tasks in parallel on one machine, a person or an agent, and the agents doing those tasks, through the CLI and the plugin. agent-task depends on git and `/bin/sh` alone; it reads no other tool's data, and every command works where no other tool is installed.

## 2. Functional requirements

### 2.1 The store

- **FR-1** — Tasks and projects live in one SQLite database, `$XDG_DATA_HOME/agent-task/tasks.db`, created with its directory on first use, and the halt in `halt.json` beside it (FR-39), the machine's limits in `limits.json` (FR-55), and the check slot in `check.lock` (FR-56). The store is machine-local and holds a brief's or a plan's path, and a brief's sha, never the file itself, which stays where it is.
- **FR-2** — An `XDG_DATA_HOME` that is unset, empty or not an absolute path counts as `$HOME/.local/share`.
- **FR-3** — A task's name is unique in the store by a database constraint, so of several `start`s of one name at once, exactly one succeeds and the rest are refused `name_taken`.
- **FR-4** — A store of a schema version this agent-task cannot read is refused `store_version` and left as it is.
- **FR-5** — A store of an earlier schema version is migrated in place by the first command that opens it. From version 1: every running task is kept with its name, repository, brief, brief sha and start time, its added time set to its start time, no session, goal, plan, priority, waits or check, and waiting after nothing; the done and dropped tasks and their commits are removed, so their names are free. From version 2: the store gains the check column, every task kept as it was with no check. From version 3: the store gains its projects, holding none, every task kept as it was in no project. From version 4, which an unreleased agent-task wrote with owner items: every task and project is kept as it was, and any owner item is dropped with every after name naming it. A migration from an earlier version also makes each later one's change.

### 2.2 Names and states

- **FR-6** — A task name is kebab-case: lowercase letters and digits in words joined by single dashes. Any other name is refused `invalid_name`.
- **FR-7** — A task is `queued`, `running` or `review`. `add` makes it queued, `start` makes it running, `review` takes a running task to review, `stop` takes a running or in-review task back to queued, and `done` removes it in any state, after which its name is free. A command on a task in a state that does not admit it is refused `wrong_state`, and one on a name the store does not hold is refused `unknown_task`, naming `start`. Each of these refusals names the task's state and the commands that state admits: `add`, `wait`, `map`, `priority`, `start` and `done` for a queued task; `wait`, `map`, `priority`, `review`, `stop` and `done` for a running one; `wait`, `map`, `priority`, `stop` and `done` for one in review.

### 2.3 add

- **FR-8** — `add <name> --repo <path> --goal <text> [--project <id>] [--plan <file>] [--priority urgent|high|medium|low] [--after <name>]... [--waits <text>] [--until <command>]` records a queued task: the repository's main working tree as `start` resolves it (FR-11); the goal; the project it belongs to (FR-47), or `null`; the plan's absolute real path, or `null`; the priority, or `null`; the tasks it waits after; what else it waits for, as text, or `null`; the check that says its wait is met, a shell command recorded as given, or `null`; and the time, as its added time. It prints the task, whose `after` lists the names it waits after that the store holds. An empty or blank `--until` is the usage error `bad_arguments`.
- **FR-9** — A `<path>` whose main working tree git cannot confirm is refused `not_a_checkout` as `start` refuses it (FR-12); a `--plan` that is not a readable file is refused `plan_unreadable`; an `--after` name the store does not hold is refused `unknown_task`, so a typo cannot read as landed; `--after` naming the task itself, and a `--priority` outside the four, are the usage error `bad_arguments`. Each records nothing.
- **FR-10** — `add` on a name the store holds queued replaces that task's repository, goal, project, plan, priority, after, waits and check, keeping its added time; on a name held running or in review it is refused `name_taken`, naming its state and what that state admits, and the task is unchanged.

### 2.4 start

- **FR-11** — `start <name> --repo <path> --brief <file> [--project <id>] [--session <id>]` records a running task: the project it belongs to (FR-47); the repository's main working tree as an absolute real path, whether `<path>` is that checkout, a directory inside it or one of its linked worktrees; the brief's absolute real path; the git blob sha of the brief's content; the session id when one is given, else `null`; and the time, as the start time. A name the store does not hold is added with that time as its added time, the project given or none, and no goal, plan, priority or waits; a queued task of that name becomes running, keeping its goal, plan, priority, waits and added time, and its project unless `--project` names one, taking the repository given, waiting after no task and with no check. It prints the task.
- **FR-12** — A `<path>` whose main working tree git cannot confirm, such as a path outside git, a bare repository, a submodule or a checkout with a separate git dir, is refused `not_a_checkout`, naming the path and the main working tree it would have been. A `<file>` that is not a readable file is refused `brief_unreadable`.
- **FR-13** — A name the store holds running or in review is refused `name_taken`, naming its state and what that state admits; the task it names is unchanged.
- **FR-14** — A queued task that waits after a name the store still holds is refused `blocked`, naming those names, `done` for each of them and `wait` for the task; the task is unchanged. A task waits after a name only while the store holds it: `done` of that name frees what waited after it, and `add` of the name again blocks them again.

### 2.5 wait

- **FR-15** — `wait <name> [--after <name>]... [--waits <text>] [--until <command>]` replaces what a task waits for: the tasks it waits after and the check that says its wait is met, on a queued task, and the text, in any state; given none of the three, it clears all three. It prints the task. `--after` or `--until` on a running or in-review task is refused `wrong_state`; an `--after` name the store does not hold is refused `unknown_task`, and the task itself as `--after`, and an empty or blank `--until`, are the usage error `bad_arguments`.

### 2.6 review

- **FR-16** — `review <name>` takes a running task to review, recording the time as its review time and keeping the rest, its brief and brief sha among them, and prints the task. On a task in review, a queued one or a name the store does not hold it is refused as FR-7 says.

### 2.7 list

- **FR-17** — `list` prints `tasks`, the running and in-review tasks oldest started first; `ready`, the queued tasks that wait after no held name and either have a check that is met or have no check and no waits text; and `waiting`, the other queued tasks. `ready` and `waiting` are each ordered by priority, urgent first and none last, then added time, then name. With `--full`, each running or in-review task prints its name, project, state, repository, goal, plan, priority, waits, added time, brief, brief sha, session, start time, its review time or `null` while it runs, and `briefChanged`: true when the brief's content no longer has the sha it started with, or the brief is gone or cannot be read; and each queued task its name, project, state, repository, goal, plan, priority, waits, added time, `after`, `until` and `untilState`, its check's result (FR-33) or `null` when it has none.

### 2.8 stop

- **FR-18** — `stop <name>` takes a running or in-review task back to queued, keeping its name, project, repository, goal, plan, priority, waits and added time, forgetting its brief, brief sha, session, start time and review time, waiting after no task and with no check, and prints the task.

### 2.9 done

- **FR-19** — `done <name>` removes a task in any state from the store, whatever became of its work, and prints the task as it was.

### 2.10 Output and the version

- **FR-20** — `--version` prints the version alone on one line and exits 0; `--version` with an argument is a usage error.
- **FR-21** — No command runs `list` (FR-17) and prints what it prints; `--help` prints the result of the command `agent-task`, `commands` and `flags`, listing each command's and flag's name, usage and summary, `--help` and `--version` among the flags, and exits 0; `--help` with an argument is a usage error.
- **FR-22** — A result is [TOON](https://toonformat.dev) on stdout, as `@toon-format/toon` 4.4.0 encodes the object of `command`, the command's name, `ok`, true, and `result`, its value, with exit 0, except that `doctor` exits 1 when a check fails (FR-26): `ok` means the command ran. An error is TOON on stderr, the object of `command`, `ok`, false, and `error`, with its `kind`, `code`, `message`, `meta` and `resolve`, where `resolve` names the act that resolves it; the exit is 1 for a refusal, 2 for a usage error and 3 for a fault. An unknown command is the usage error `unknown_command`, and a command given a missing, empty, extra or unknown argument is the usage error `bad_arguments`.

### 2.11 The Claude Code plugin

- **FR-23** — *Retired.*
- **FR-24** — Whenever a session starts, resumes, clears or compacts, the `cniska-task` plugin puts its note, `plugin/hooks/note.md`, in the session's context: queued and running work lives in agent-task, not in a ledger, a notes file or a plan; `add`, `start`, `review` and `done` queue, start, hand back and close a task; a test, check, verify, lint, typecheck or build runs through `check`; and `halt` stops all agent work until the owner runs `resume`. While a halt is raised, as `halted` reports it (FR-41), a heading saying all agent work is halted, to make no change, state a report and stop, and that only the owner lifts it, then the refusal as `halted` prints it, come before the note. When the working directory holds the brief of a running or in-review task, the running and in-review tasks follow the note as `list --started` (FR-34) prints them, `briefChanged` included, under a heading. The session hook leaves that decision to `list --started --brief-under` (FR-35) and parses none of agent-task's output.
- **FR-25** — The session hook prints one line saying the halt could not be checked, alone when `agent-task` is not on `PATH` or `--version` fails, and before the note when `halted` exits other than 0 or 1, such as `unknown_command` from an older `agent-task`. It prints the note alone when `list --started --brief-under` is refused, such as `no_brief_under`, `store_version` or `bad_arguments` from an older `agent-task`, or when the hook's input names no directory; it exits 0 in every case. Without `jq` on `PATH`, the hook prints the note and leaves a line on stderr naming `jq`. The hooks see the `PATH` Claude Code started with; [`docs/plugin.md`](docs/plugin.md) says how to check that `PATH` with `doctor`.

### 2.12 doctor

- **FR-26** — `doctor` reports its checks, each with a name, a state of `ok`, `warn` or `fail`, a detail and a fix (`null` when it passes); it exits 1 when a check fails and 0 otherwise. It reads only the store, each task's repository, each running or in-review task's brief, each plan a task names, git and `PATH`: it writes no task and no schema, makes no store where there is none, runs no task's check, and contacts no git remote.
- **FR-27** — The store check passes when there is no store yet, since `add` and `start` create one, and when the store is of this version; it warns naming `list` when the store is of version 1, 2, 3 or 4, which `list` migrates (FR-5); it fails with the refusal's fix when the store is of a version this agent-task cannot read (FR-4), cannot be opened or stays locked. Unless it passes, no task is checked.
- **FR-28** — `doctor` looks through `PATH` for an executable `bash`, `agent-task` and `jq`, which the plugin's hooks need (FR-25, FR-43, C-3), and `git`, and runs none of them but git. Each detail names where the program was found, or the directories searched. A missing hook program warns, naming what the hooks leave out without it, since `doctor` cannot tell whether the plugin is installed; a missing git fails.
- **FR-29** — For each task, the running and in-review ones oldest started first and then the queued ones in `list`'s order, `doctor` checks its repository: one that is not a directory fails naming `done`; without git on `PATH` the repository warns as unchecked; one that is not a checkout git can confirm, or is no longer its own main working tree, warns naming `done`. Whether it has an origin is not `doctor`'s to find. For each running or in-review task, a brief that is not a readable file warns naming `stop`; for each task with a plan, a plan that is not a readable file warns naming `add` again.

### 2.13 The release build

- **FR-30** — `scripts/build-compiled.sh <outfile> [<target>]` compiles the CLI, for the machine it runs on or for `darwin-arm64` or `linux-x64`, into one executable that carries the version and SQLite through Bun's driver, so it runs every command with no checkout of agent-task and no Bun on the machine. `scripts/build-release.sh` compiles only the target `TARGET` names, refuses to run on a machine of another platform, and runs the smoke on that build before it packs it.
- **FR-31** — `install.sh`, run by `curl … | sh`, downloads the latest release's build for this platform, checks it against its published sha256, runs it for its version, and installs it as `~/.local/bin/agent-task`, writing it beside that path and renaming it into place. A download that fails, does not match its checksum, or reports a version that is not `x.y.z` installs nothing. Run again, it replaces the install.
- **FR-32** — The npm package `@cniska/agent-task` installs the build for its platform from `@cniska/agent-task-darwin-arm64` or `@cniska/agent-task-linux-x64`, finds it where `npm` or `bun` installed it, and runs it with the arguments it was given, exiting as it exits, with no `node` or `bun` on `PATH`. On another platform, or with the platform package missing, it refuses with `no_build_for_platform` or `platform_package_missing`; with a platform build that is not executable, with `binary_failed`. Each refusal is the error on stderr that FR-22 gives, exiting 1.

### 2.14 Wait checks

- **FR-33** — A queued task's check runs as `/bin/sh -c <command>`, the shell by its absolute path, in the task's repository, with the environment the CLI has, its input and output discarded, under a time limit the entry sets, five seconds. The result is `met` on exit 0, `unmet` on exit 1 through 125, `timed_out` when the limit passes, and `failed` on exit 126 or above, on a signal, when the shell cannot start or when the repository is gone. `list` runs every queued task's check on every call, and writes nothing: `--full` prints a result, which is never stored. `add` and `wait` print `until` and run no check.
- **FR-34** — `list --started` prints `counts` and `tasks` alone, as FR-17 defines it, reading no queued task and running no check; `list --started` with any other argument than `--brief-under`, `--project` and `--full` is `bad_arguments`.
- **FR-35** — `list --started --brief-under <dir>` prints what `list --started` prints when the brief of a running or in-review task sits under `<dir>`'s real path, and otherwise, a `<dir>` that does not exist included, is refused `no_brief_under`, naming `<dir>` and `list --started`. `--brief-under` without `--started`, or with an empty value, is `bad_arguments`.

### 2.15 Default views

- **FR-36** — A result that lists leads with `counts`: `list` with how many tasks are `running`, in `review`, `ready` and `waiting`, followed by `halt` (FR-42); `list --started` with how many are `running` and in `review`; `doctor` with how many checks are `ok`, `warn` and `fail`; and `project list` with how many `projects` (FR-45).
- **FR-37** — Without `--full`, `list` prints each running or in-review task with its name, project, state, brief and `briefChanged`, and each queued task with its name, project and repository, each list a TOON table; no field it prints by default is ever `null` but the project of a task that belongs to none.
- **FR-38** — Without `--full`, `doctor` prints only the checks that warn or fail, each with its name, state, detail and fix, as a TOON table, empty when every check passes; with `--full`, every check.

### 2.16 The halt

- **FR-39** — `halt <reason>` raises one halt of all agent work on the machine, recording its reason and the time in `halt.json` in the store's directory, which it creates, published whole so no reader sees part of it, and prints it as `halt`, its `state` `raised`, `reason` and `raised`. With a halt raised or unreadable it records nothing and prints that halt unchanged. Any caller may raise it. A missing, blank or second reason is `bad_arguments`.
- **FR-40** — `resume` lifts the halt, the owner's act, removing its record, and prints it as it was, or `state` `none` when none was recorded. A record it cannot remove, such as a directory, is refused `halt_unremovable`, naming its path, and stays.
- **FR-41** — `halted` prints `halt` with `state` `none` when no halt is recorded, and while one is raised is refused `halted`, naming its reason and time, and saying to make no change, state a report and stop, and that only the owner lifts it with `resume`. A record that cannot be read, is not a file or is a link to nothing, or is not JSON of exactly a non-blank `reason` and a textual `raised`, counts as raised: refused `halted` naming its path and why it cannot be read.
- **FR-42** — While a halt is raised or unreadable, `add`, `start`, `wait`, `map`, `priority`, `project add`, `project remove` and `check` are refused `halted` as FR-41 words it, and record nothing; the other commands work. `list` prints `halt` after `counts`: `state` `none`; `raised` with its `reason` and `raised`; or `unreadable` with its `path` and `detail`.
- **FR-43** — The plugin's `PreToolUse` hook is registered for the tools `Edit`, `Write`, `NotebookEdit`, `Bash`, `PowerShell`, `Monitor`, `Agent`, `Workflow` and `EnterWorktree`, and names no other plugin's tools. It asks `halted`: when that exits 0, or other than 1, or `agent-task` is not on `PATH`, or `agent-task --version` fails, the call goes through. While a halt is raised it refuses the call, exit 2, with a line on stderr saying all agent work is halted, to make no further change, state a report and stop, and that only the owner lifts it, then the refusal as `halted` prints it; except a `Bash` or `PowerShell` command that runs only `agent-task`: the word `agent-task`, then arguments holding no `;`, `&`, `|`, `<`, `>`, `$`, backtick, parenthesis, brace, backslash or control character. While a halt is raised, a call whose input the hook cannot read, without `jq` or not JSON, is refused. With no halt, a `Bash`, `PowerShell` or `Monitor` command goes on to the check gate (FR-58). Every tool it is not registered for goes through.

### 2.17 Projects

- **FR-44** — `project add <id> --name <text> --repo <path> --dir <dir>` records a project: its id, in a task name's form (FR-6), else refused `invalid_project`; its readable name; the repository's main working tree, resolved and refused `not_a_checkout` as `start` does (FR-11, FR-12); and the absolute real path of the directory its briefs and plans live in, refused `dir_missing` when it is not a directory. It prints the project. On an id the store holds it replaces the name, repository and directory, and the tasks that belong to it still do. A missing or blank flag is `bad_arguments`. Each refusal records nothing.
- **FR-45** — `project list` prints `counts`, with how many `projects`, then `projects`, each with its id, name, repo and dir, ordered by id, as a TOON table.
- **FR-46** — `project remove <id>` removes a project no task belongs to and prints it. While a task belongs to it, it is refused `project_in_use`, naming those tasks and, for each, `map` and `done`, and the project stays; an id the store does not hold is refused `unknown_project`.
- **FR-47** — A task belongs to one project the store holds, or to none, and agent-task never infers one from a repository or a directory. `add`, `start` and `map` name it; a project the store does not hold is refused `unknown_project`, naming `project add` and `project list`, and records nothing. `map <name> --project <id>` makes a task in any state belong to that project and prints the task; a name the store does not hold is refused `unknown_task`.
- **FR-48** — `list --project <id>`, alone or with `--started` and `--brief-under`, prints only the tasks that belong to that project, its counts included; a project the store does not hold is refused `unknown_project`. Every task `list` prints carries its `project`, `null` when it belongs to none.

### 2.18 The update check

- **FR-49** — Before any command, a usage error included, agent-task tells the agent running it when a newer release is out on the channel it was installed through: one line on stderr, `agent-task <latest> is out (running <version>): run <upgrade>; if you cannot, tell the user.`, printed on every command while the latest version known for that channel is newer than the running one by number, whether or not that command asked the channel. Stdout and the exit code are as they would be without it.
- **FR-50** — The channel is read from the real path of the running binary, starting no process: Homebrew for a binary in the `agent-task` formula's `Cellar`, npm for the platform build nested under the global `@cniska/agent-task` package, Bun for the platform build in Bun's global install, and the curl installer for `~/.local/bin/agent-task` (FR-31). Their upgrades are `brew upgrade agent-task`, `npm update -g @cniska/agent-task`, `bun update -g @cniska/agent-task`, and the README's curl line run again. Any other binary, a checkout's or one placed by hand, is on no channel, and agent-task asks nothing and prints no line.
- **FR-51** — The latest version is what the channel serves: for Homebrew the tag in the `url` lines of `Formula/agent-task.rb` in `cniska/homebrew-tap`, for npm and Bun the registry's `latest` tag, and for the curl installer the latest GitHub release. agent-task asks at most once a day per machine, under a time limit of one second the entry sets, and keeps the time it asked and the latest version of each channel in `$XDG_STATE_HOME/agent-task/update-check.json`, with an `XDG_STATE_HOME` that is unset, empty or not absolute counting as `$HOME/.local/state`. An answer that fails, times out or does not name one version counts as that day's check and prints nothing of its own; a state file it cannot read counts as no check; where it cannot record the day's check, it asks nothing, prints the line only from the latest version the state file already names, and throws nothing.
- **FR-52** — No check runs and no line prints while `CI` or `AGENT_TASK_NO_UPDATE_CHECK` is set to a value that is not blank. The test environment and the acceptance suite set `AGENT_TASK_NO_UPDATE_CHECK`, and the plugin's hooks export it, so what a hook captures and shows, a halt refusal included, stays the same.

### 2.19 Priority

- **FR-53** — `priority <name> urgent|high|medium|low|none` sets the priority of a task in any state, or with `none` clears it, keeping every other field, and prints the task. A name the store does not hold is refused `unknown_task`, and a missing level, a second one or one outside the five are the usage error `bad_arguments`; each records nothing.

### 2.20 A busy machine

- **FR-54** — `start` reads how busy the machine is from the operating system on every call, on any macOS or Linux machine with nothing set up: the 1-minute load average divided by the machine's CPU cores, and the share of physical memory available to a new process without swapping, reclaimable cache included, which Linux reports as `MemAvailable` in `/proc/meminfo` and macOS as the `kern.memorystatus_level` sysctl. It is refused `machine_busy` while the load per core is above the machine's `maxLoadPerCore` or the available share below its `minAvailableMemory`, and records nothing. The refusal names each reading, each limit, which reading passed its limit and the limits file, and says to start nothing now and retry the start once the machine is less busy, and that only the owner changes the limits. A machine whose readings cannot be taken is refused `machine_unread`. No flag sets a limit or a reading, and the limits are read from beside the store, so a start under another `XDG_DATA_HOME` reaches only another store; of the other commands only `check` reads the machine (FR-56).
- **FR-55** — The limits are the machine's own, in `limits.json` in the store's directory (FR-1): a JSON object of `maxLoadPerCore`, a number of at least 0, and `minAvailableMemory`, a share from 0 to 1, each optional. A limit the file does not set, or a machine with no file, takes the default: 0.7 load per core and 0.15 of memory available. A file that is not such an object, a directory or a link to nothing included, is refused `limits_unreadable` by `start` and `check`, naming its path and why.

### 2.21 Checks

- **FR-56** — `check <command>` runs a test, check, verify, lint, typecheck or build: one shell command, given as one argument, run as `/bin/sh -c <command>` in the working directory with the CLI's environment, its input, output and error passed through, and its exit code agent-task's, or 128 plus the signal's number when a signal ends it. Before the run, it takes the machine's one check slot, an exclusive lock on `check.lock` in the store's directory, which it creates, waiting while another check holds it; then, holding it, waits while the machine is over its limits, read as `start` reads them (FR-54, FR-55). While it waits it prints a line on stderr naming what it waits on: the slot's holder, by its process, start time, command and directory, or each reading over its limit; a line again only when that changes. The check inherits the lock, so the slot is free once the check and every process still holding it end, however each ends, and not before; agent-task itself killed frees nothing a check it started still holds. It prints no result of its own. While a halt is raised or unreadable it is refused `halted`, before it waits, on every look while it waits and before it runs, running nothing and freeing the slot. A machine whose readings cannot be taken is refused `machine_unread` and an unreadable limits file `limits_unreadable`. No flag skips the slot or the wait: a missing, blank or second command, or any flag, is `bad_arguments`. The slot and the limits are read from beside the store, so a check under another `XDG_DATA_HOME` takes only another store's slot.
- **FR-57** — `gate <command>` prints `gated` true when a shell command runs no check but through `check`, and otherwise is refused `check_ungated`, naming the command, each check it runs, and `agent-task check` with the command quoted for the shell as the act. A check is a simple command, wherever it sits in a list, a pipeline, a subshell, a brace group, a command substitution or the script of `sh`, `bash`, `zsh` or `dash -c`, and behind `cd`, assignments, redirections and the wrappers `env`, `time`, `nice`, `timeout`, `nohup`, `command`, `exec`, `sudo`, `xargs` and `mise exec … --`: `mise run` or `mise r` of a task whose name, or its name's first `:`-separated part, is `test`, `check`, `verify`, `lint`, `typecheck` or `build`; `bun`, `npm`, `pnpm` or `yarn` `run` of such a script, and `pnpm` or `yarn` naming one directly; `bun test`, `npm test`, `flutter test`, `dart test`, `cargo test`, `busted` and `xcodebuild`. A command that holds `--watch`, or a task one of whose `:`-separated parts is `watch`, is a watcher and no check. `agent-task check`'s argument is no check of its own, but a command substitution the outer shell expands in it is read like any other. Quoted text is read as one word and a here-document's body as data, following only its command substitutions when its delimiter is unquoted, so a check named inside a commit message, an `echo`, a `grep` pattern or a file a here-document writes is none. A missing, blank or second command is `bad_arguments`.
- **FR-58** — The plugin's `PreToolUse` hook passes a `Bash`, `PowerShell` or `Monitor` command to `gate`; while `gate` refuses it and `agent-task --version` succeeds, it refuses the call, exit 2, with a line on stderr saying the command runs a check outside `agent-task check` and that checks on this machine run one at a time, only while it is under its limits, through `agent-task check`, then the refusal as `gate` prints it. When `gate` exits other than 1, `agent-task` is not on `PATH`, or the hook cannot read the command, the call goes through. It does so in every session the plugin runs in, a coordinator's included; a shell the owner runs has no hook and is never held.

## 3. Non-functional requirements

- **NF-1** — The tests never read or write the real home: `HOME` and the XDG directories point at scratch directories.
- **NF-2** — Every command reads the store, the filesystem and git afresh, and `start` and `check` the machine's readings and limits. Only the update check keeps a result between commands: the time it asked and the latest version of each channel, in `update-check.json` (FR-51).
- **NF-3** — Every command of the CLI, run from a checkout or as the release binary, runs with git as the only program on `PATH`; a queued task's check, and the command `check` runs, run under `/bin/sh` by its absolute path. The npm package's launcher also needs a POSIX shell and the system's `uname`, `readlink`, `dirname` and `sed` on `PATH`.

## 4. Out of scope

- Worktrees: agent-task never creates, reads or checks one; a task may share its worktree's name.
- Whether a task's work landed: `done` takes the caller's word, and git's own history holds what landed.
- A record of agent sessions beyond the id `start` is given, and notes on how a task is going beyond what it waits for.
- Showing one task, a record of removed tasks, who acted, experiments, sub-tasks and a UI.

- **AC-54** — A `check` whose command starts a background process that waits for a file, then is killed with `kill -9 $$`: exit 137, and a second `check` waits for the slot until that background process ends, then runs; a `check` whose agent-task process is killed with SIGKILL while its command waits for a file: a second `check` waits for the slot until that command ends, then runs. (FR-56)
- **AC-55** — With a halt raised, `check`: refused `halted`, running nothing; with a limits file of `maxLoadPerCore` 0, a waiting `check`: once a halt is raised, refused `halted`, running nothing, and after `resume` a `check` runs. (FR-42, FR-56)
- **AC-56** — `gate` of `cd app && mise run check`: refused `check_ungated` naming `mise run check` and `agent-task check 'cd app && mise run check'`; of `agent-task check 'cd app && mise run check'`, `git commit -m 'bun test'` and `mise run dev`: `gated` true; with no command: exit 2 with `bad_arguments`. (FR-57)
- **AC-57** — Run the `PreToolUse` hook as `hooks.json` registers it, with only a shell, bash, git, `jq` and `agent-task` on `PATH`: a `Bash` call of `cd app && mise run check`, a `PowerShell` call of `bun test` and a `Monitor` call of `flutter test` each exit 2 with the line that the command runs a check outside `agent-task check` and the refusal naming `agent-task check`; a `Bash` call of `agent-task check 'mise run check'` and of `ls`, and an `Edit`, exit 0 printing nothing; with an `agent-task` whose `gate` is `unknown_command`, and with no `agent-task` on `PATH`, the `Bash` call of `mise run check` exits 0. (FR-58)

## 6. Deliverables

- **D-1** — The `agent-task` CLI, run by Bun from a checkout through `bin/agent-task` and linked onto `PATH` by `mise install` in the primary checkout; and beside it the release binary `scripts/build-compiled.sh` compiles, for darwin-arm64 and linux-x64, shipped by a GitHub release with `install.sh`, by the npm packages and by the `cniska/tap` Homebrew formula.
- **D-2** — `README.md`, `AGENTS.md`, `src/README.md`, `docs/commands.md`, `docs/plugin.md`, `docs/development.md`, `docs/releasing.md`, `CONTRIBUTING.md` and this spec.
- **D-3** — The test suite, run by `bun run check`, and the acceptance suite, run by `bun run acceptance`, whose test names cite the criteria in §5. The acceptance suite drives the CLI, the plugin's hooks as its `hooks.json` registers them, the compiled release binary, `scripts/build-release.sh`, `install.sh` against a stand-in for the release downloads, and the npm packages through their launcher, from outside.
- **D-4** — The `cniska-task` Claude Code plugin in `plugin/`.
- **D-5** — The release, through agent-ship's reusable release workflow, which `release.yml` calls pinned to an agent-ship release's commit, with the channels and build commands `ship.toml` names. It builds and smoke-tests each target on a runner of that platform. It installs the published npm packages from the registry on both platforms, through npm and through Bun, and runs `scripts/smoke.sh` on each install with neither Node nor Bun on `PATH`. A dispatch of `release.yml` is a dry run that publishes nothing, and two runs of one tag never publish at once. Each file the release attaches carries a build provenance attestation from that workflow at the tag, and the release is published only once every file is attached, so a release with release immutability on keeps the files it published, as [`docs/releasing.md`](docs/releasing.md#what-a-release-guarantees) says.

## 7. Constraints (fixed)

- **C-1** — TypeScript on Bun, which mise installs, with SQLite through Bun's own driver and TOON through `@toon-format/toon`.
- **C-2** — git and `/bin/sh`, which runs a queued task's check and the command `check` runs, are the programs the CLI runs, from a checkout or as the release binary. The npm package's launcher runs `uname`, `readlink`, `dirname` and `sed` before it hands over to the CLI.
- **C-3** — The plugin brings neither Bun nor the CLI. Its hooks are shell that runs with a POSIX shell, bash, `jq` and `agent-task` alone, and it reads the store only through the CLI.
