# agent-task Specification

> The coding-agent tasks on one machine, queued, running or in review, recorded so they can be listed in the order to start them, checked against their briefs, stopped and removed.

This document states what must hold, not how. [`README.md`](README.md) has the install and a summary of every command, [`docs/commands.md`](docs/commands.md) every command, its flags and output, and the store, and [`src/README.md`](src/README.md) maps the modules that meet these requirements.

## 1. Purpose & context

Coding agents run in parallel on one machine, each on a task started from a brief, a file of instructions for that task, and the tasks still to start wait in a queue. agent-task records each task: its name, the repository the work lands in; queued, its goal, its plan, its priority, the tasks it waits after, what else it waits for and the check that says its wait is met; and, from the time it runs, the brief's path, the git blob sha of the brief's content when the work started, the session that started it and, once the work is handed back, the time it went to review. It refuses a second task under a name it holds, refuses to start a task while one it waits after is still held, lists the running and in-review tasks and flags one whose brief no longer has that sha or is gone or unreadable, runs each queued task's check and lists the queued tasks in the order to start them, the ready apart from the waiting, takes a running or in-review task back to queued when its work pauses or its review sends it back, and removes a task when its work is over, however it ended. `doctor` reports what agent-task and its plugin need in order to work, with a fix for each failure. The `cniska-task` Claude Code plugin puts the running and in-review tasks, each with whether its brief changed, in a session's context where the session's working directory holds one of their briefs.

**Primary user:** whoever runs coding-agent tasks in parallel on one machine, a person or an agent, and the agents doing those tasks, through the CLI and the plugin. agent-task depends on git and `/bin/sh` alone; it reads no other tool's data, and every command works where no other tool is installed.

## 2. Functional requirements

### 2.1 The store

- **FR-1** — Tasks live in one SQLite database, `$XDG_DATA_HOME/agent-task/tasks.db`, created with its directory on first use. The store is machine-local and holds a brief's or a plan's path, and a brief's sha, never the file itself, which stays where it is.
- **FR-2** — An `XDG_DATA_HOME` that is unset, empty or not an absolute path counts as `$HOME/.local/share`.
- **FR-3** — A task's name is unique in the store by a database constraint, so of several `start`s of one name at once, exactly one succeeds and the rest are refused `name_taken`.
- **FR-4** — A store of a schema version this agent-task cannot read is refused `store_version` and left as it is.
- **FR-5** — A store of an earlier schema version is migrated in place by the first command that opens it. From version 1: every running task is kept with its name, repository, brief, brief sha and start time, its added time set to its start time, no session, goal, plan, priority, waits or check, and waiting after nothing; the done and dropped tasks and their commits are removed, so their names are free. From version 2: the store gains the check column, every task kept as it was with no check.

### 2.2 Names and states

- **FR-6** — A task name is kebab-case: lowercase letters and digits in words joined by single dashes. Any other name is refused `invalid_name`.
- **FR-7** — A task is `queued`, `running` or `review`. `add` makes it queued, `start` makes it running, `review` takes a running task to review, `stop` takes a running or in-review task back to queued, and `done` removes it in any state, after which its name is free. A command on a task in a state that does not admit it is refused `wrong_state`, and one on a name the store does not hold is refused `unknown_task`, naming `start`. Each of these refusals names the task's state and the commands that state admits: `add`, `wait`, `start` and `done` for a queued task; `wait`, `review`, `stop` and `done` for a running one; `wait`, `stop` and `done` for one in review.

### 2.3 add

- **FR-8** — `add <name> --repo <path> --goal <text> [--plan <file>] [--priority urgent|high|medium|low] [--after <name>]... [--waits <text>] [--until <command>]` records a queued task: the repository's main working tree as `start` resolves it (FR-11); the goal; the plan's absolute real path, or `null`; the priority, or `null`; the tasks it waits after; what else it waits for, as text, or `null`; the check that says its wait is met, a shell command recorded as given, or `null`; and the time, as its added time. It prints the task, whose `after` lists the names it waits after that the store holds. An empty or blank `--until` is the usage error `bad_arguments`.
- **FR-9** — A `<path>` whose main working tree git cannot confirm is refused `not_a_checkout` as `start` refuses it (FR-12); a `--plan` that is not a readable file is refused `plan_unreadable`; an `--after` name the store does not hold is refused `unknown_task`, so a typo cannot read as landed; `--after` naming the task itself, and a `--priority` outside the four, are the usage error `bad_arguments`. Each records nothing.
- **FR-10** — `add` on a name the store holds queued replaces that task's repository, goal, plan, priority, after, waits and check, keeping its added time; on a name held running or in review it is refused `name_taken`, naming its state and what that state admits, and the task is unchanged.

### 2.4 start

- **FR-11** — `start <name> --repo <path> --brief <file> [--session <id>]` records a running task: the repository's main working tree as an absolute real path, whether `<path>` is that checkout, a directory inside it or one of its linked worktrees; the brief's absolute real path; the git blob sha of the brief's content; the session id when one is given, else `null`; and the time, as the start time. A name the store does not hold is added with that time as its added time and no goal, plan, priority or waits; a queued task of that name becomes running, keeping its goal, plan, priority, waits and added time, taking the repository given, waiting after no task and with no check. It prints the task.
- **FR-12** — A `<path>` whose main working tree git cannot confirm, such as a path outside git, a bare repository, a submodule or a checkout with a separate git dir, is refused `not_a_checkout`, naming the path and the main working tree it would have been. A `<file>` that is not a readable file is refused `brief_unreadable`.
- **FR-13** — A name the store holds running or in review is refused `name_taken`, naming its state and what that state admits; the task it names is unchanged.
- **FR-14** — A queued task that waits after a name the store still holds is refused `blocked`, naming those names, `done` for each of them and `wait` for the task; the task is unchanged. A task waits after a name only while the store holds it: `done` of that name frees what waited after it, and `add` of the name again blocks them again.

### 2.5 wait

- **FR-15** — `wait <name> [--after <name>]... [--waits <text>] [--until <command>]` replaces what a task waits for: the tasks it waits after and the check that says its wait is met, on a queued task, and the text, in any state; given none of the three, it clears all three. It prints the task. `--after` or `--until` on a running or in-review task is refused `wrong_state`; an `--after` name the store does not hold is refused `unknown_task`, and the task itself as `--after`, and an empty or blank `--until`, are the usage error `bad_arguments`.

### 2.6 review

- **FR-16** — `review <name>` takes a running task to review, recording the time as its review time and keeping the rest, its brief and brief sha among them, and prints the task. On a task in review, a queued one or a name the store does not hold it is refused as FR-7 says.

### 2.7 list

- **FR-17** — `list` prints `tasks`, the running and in-review tasks oldest started first; `ready`, the queued tasks that wait after no held name and either have a check that is met or have no check and no waits text; and `waiting`, the other queued tasks. `ready` and `waiting` are each ordered by priority, urgent first and none last, then added time, then name. With `--full`, each running or in-review task prints its name, state, repository, goal, plan, priority, waits, added time, brief, brief sha, session, start time, its review time or `null` while it runs, and `briefChanged`: true when the brief's content no longer has the sha it started with, or the brief is gone or cannot be read; and each queued task its name, state, repository, goal, plan, priority, waits, added time, `after`, `until` and `untilState`, its check's result (FR-33) or `null` when it has none.

### 2.8 stop

- **FR-18** — `stop <name>` takes a running or in-review task back to queued, keeping its name, repository, goal, plan, priority, waits and added time, forgetting its brief, brief sha, session, start time and review time, waiting after no task and with no check, and prints the task.

### 2.9 done

- **FR-19** — `done <name>` removes a task in any state from the store, whatever became of its work, and prints the task as it was.

### 2.10 Output and the version

- **FR-20** — `--version` prints the version alone on one line and exits 0; `--version` with an argument is a usage error.
- **FR-21** — No command runs `list` (FR-17) and prints what it prints; `--help` prints the result of the command `agent-task`, `commands` and `flags`, listing each command's and flag's name, usage and summary, `--help` and `--version` among the flags, and exits 0; `--help` with an argument is a usage error.
- **FR-22** — A result is [TOON](https://toonformat.dev) on stdout, as `@toon-format/toon` 4.4.0 encodes the object of `command`, the command's name, `ok`, true, and `result`, its value, with exit 0, except that `doctor` exits 1 when a check fails (FR-26): `ok` means the command ran. An error is TOON on stderr, the object of `command`, `ok`, false, and `error`, with its `kind`, `code`, `message`, `meta` and `resolve`, where `resolve` names the act that resolves it; the exit is 1 for a refusal, 2 for a usage error and 3 for a fault. An unknown command is the usage error `unknown_command`, and a command given a missing, empty, extra or unknown argument is the usage error `bad_arguments`.

### 2.11 The Claude Code plugin

- **FR-23** — *Retired.*
- **FR-24** — When a session starts, resumes, clears or compacts in a working directory that holds the brief of a running or in-review task, the `cniska-task` plugin puts the running and in-review tasks in the session's context as `list --started` (FR-34) prints them, `briefChanged` included. Elsewhere it prints nothing. The hook leaves that decision to `list --started --brief-under` (FR-35) and parses none of agent-task's output.
- **FR-25** — The hook prints nothing when `agent-task` is not on `PATH`, when `list --started --brief-under` is refused, such as `no_brief_under`, `store_version` or `bad_arguments` from an older `agent-task`, or when the hook's input names no directory, and it exits 0 in every case. Without `jq` on `PATH`, the hook leaves a note on stderr and nothing else. The hook sees the `PATH` Claude Code started with; [`docs/plugin.md`](docs/plugin.md) says how to check that `PATH` with `doctor`.

### 2.12 doctor

- **FR-26** — `doctor` reports its checks, each with a name, a state of `ok`, `warn` or `fail`, a detail and a fix (`null` when it passes); it exits 1 when a check fails and 0 otherwise. It reads only the store, each task's repository, each running or in-review task's brief, each plan a task names, git and `PATH`: it writes no task and no schema, makes no store where there is none, runs no task's check, and contacts no remote.
- **FR-27** — The store check passes when there is no store yet, since `add` and `start` create one, and when the store is of this version; it warns naming `list` when the store is of version 1 or 2, which `list` migrates (FR-5); it fails with the refusal's fix when the store is of a version this agent-task cannot read (FR-4), cannot be opened or stays locked. Unless it passes, no task is checked.
- **FR-28** — `doctor` looks through `PATH` for an executable `bash`, `agent-task` and `jq`, which the plugin's hook needs (FR-25, C-3), and `git`, and runs none of them but git. Each detail names where the program was found, or the directories searched. A missing hook program warns, naming the hook that goes silent without it, since `doctor` cannot tell whether the plugin is installed; a missing git fails.
- **FR-29** — For each task, the running and in-review ones oldest started first and then the queued ones in `list`'s order, `doctor` checks its repository: one that is not a directory fails naming `done`; without git on `PATH` the repository warns as unchecked; one that is not a checkout git can confirm, or is no longer its own main working tree, warns naming `done`. Whether it has an origin is not `doctor`'s to find. For each running or in-review task, a brief that is not a readable file warns naming `stop`; for each task with a plan, a plan that is not a readable file warns naming `add` again.

### 2.13 The release build

- **FR-30** — `scripts/build-compiled.sh <outfile>` compiles the CLI into one executable that carries the version and SQLite through Bun's driver, so it runs every command with no checkout of agent-task and no Bun on the machine.
- **FR-31** — `install.sh`, run by `curl … | sh`, downloads the latest release's build for this platform, checks it against its published sha256, runs it for its version, and installs it as `~/.local/bin/agent-task`, writing it beside that path and renaming it into place. A download that fails, does not match its checksum, or reports a version that is not `x.y.z` installs nothing. Run again, it replaces the install.
- **FR-32** — The npm package `@cniska/agent-task` installs the build for its platform from `@cniska/agent-task-darwin-arm64` or `@cniska/agent-task-linux-x64`, finds it where `npm` or `bun` installed it, and runs it with the arguments it was given, exiting as it exits, with no `node` or `bun` on `PATH`. On another platform, or with the platform package missing, it refuses with `no_build_for_platform` or `platform_package_missing`; with a platform build that is not executable, with `binary_failed`. Each refusal is the error on stderr that FR-22 gives, exiting 1.

### 2.14 Wait checks

- **FR-33** — A queued task's check runs as `/bin/sh -c <command>`, the shell by its absolute path, in the task's repository, with the environment the CLI has, its input and output discarded, under a time limit the entry sets, five seconds. The result is `met` on exit 0, `unmet` on exit 1 through 125, `timed_out` when the limit passes, and `failed` on exit 126 or above, on a signal, when the shell cannot start or when the repository is gone. `list` runs every queued task's check on every call, and writes nothing: `--full` prints a result, which is never stored. `add` and `wait` print `until` and run no check.
- **FR-34** — `list --started` prints `counts` and `tasks` alone, as FR-17 defines it, reading no queued task and running no check; `list --started` with any other argument than `--brief-under` and `--full` is `bad_arguments`.
- **FR-35** — `list --started --brief-under <dir>` prints what `list --started` prints when the brief of a running or in-review task sits under `<dir>`'s real path, and otherwise, a `<dir>` that does not exist included, is refused `no_brief_under`, naming `<dir>` and `list --started`. `--brief-under` without `--started`, or with an empty value, is `bad_arguments`.

### 2.15 Default views

- **FR-36** — A result that lists leads with `counts`: `list` with how many tasks are `running`, in `review`, `ready` and `waiting`; `list --started` with how many are `running` and in `review`; and `doctor` with how many checks are `ok`, `warn` and `fail`.
- **FR-37** — Without `--full`, `list` prints each running or in-review task with its name, state, brief and `briefChanged`, and each queued task with its name and repository, each list a TOON table; no field it prints by default is ever `null`.
- **FR-38** — Without `--full`, `doctor` prints only the checks that warn or fail, each with its name, state, detail and fix, as a TOON table, empty when every check passes; with `--full`, every check.

## 3. Non-functional requirements

- **NF-1** — The tests never read or write the real home: `HOME` and the XDG directories point at scratch directories.
- **NF-2** — Every command reads the store, the filesystem and git afresh; nothing is remembered between commands.
- **NF-3** — Every command of the CLI, run from a checkout or as the release binary, runs with git as the only program on `PATH`; a queued task's check runs under `/bin/sh` by its absolute path. The npm package's launcher also needs a POSIX shell and the system's `uname`, `readlink`, `dirname` and `sed` on `PATH`.

## 4. Out of scope

- Worktrees: agent-task never creates, reads or checks one; a task may share its worktree's name.
- Whether a task's work landed: `done` takes the caller's word, and git's own history holds what landed.
- A record of agent sessions beyond the id `start` is given, and notes on how a task is going beyond what it waits for.
- Showing one task, a record of removed tasks, who acted, experiments, sub-tasks and a UI.

## 5. Acceptance criteria

- **AC-1** — `start task-a` in a repository with a brief, then `start task-b` with `--session session-1`: each task printed with the repository, the brief, its blob sha, its session or `null`, no goal, plan, priority or waits, and the time as both added and start time, and the store at `$XDG_DATA_HOME/agent-task/tasks.db`; `list` prints both in `tasks` with `briefChanged` false and `ready` and `waiting` empty. (FR-1, FR-11, FR-17)
- **AC-2** — With `XDG_DATA_HOME` unset, empty and relative: the store is at `$HOME/.local/share/agent-task/tasks.db`. (FR-1, FR-2)
- **AC-3** — `start` from a directory inside the repository and from a linked worktree: each records the main working tree; remove the worktree, and `done` removes the task, printing it as it was. (FR-11, FR-19)
- **AC-4** — `start` on a path outside git, a bare repository and a submodule: `not_a_checkout`, and `list` stays empty. (FR-12)
- **AC-5** — `start` with names in each invalid form, with a missing brief, an unreadable brief and a directory as the brief: `invalid_name` and `brief_unreadable`, and `list` stays empty. (FR-6, FR-12)
- **AC-6** — `start` of a running name: `name_taken` naming `running`, `wait`, `review`, `stop` and `done`, and `list` still prints it unchanged; `start` of a stopped name from another repository with a session: running again with its first added time, the new repository and session, and a later start time; `done` it, and `start` of the name again: a fresh task with no session and its added time equal to its start time. (FR-7, FR-11, FR-13, FR-19)
- **AC-7** — Several `start`s of one name at once, each from its own repository: exactly one succeeds, the rest are `name_taken`, and `list` prints the one. (FR-3)
- **AC-8** — Three running tasks, a removed one and a stopped one; amend one brief and delete another between two `list`s: the second prints the three running tasks oldest first, flagging the amended and the deleted brief, and `ready` holds the stopped one. (FR-17, FR-18, NF-2)
- **AC-9** — `stop` a task started with a session: the task queued with its name, repository and added time, null goal, plan, priority and waits, and nothing after; `stop` it again: `wrong_state` naming `queued`, `add`, `wait`, `start` and `done`; `done` it: printed as queued; `done` a running task: printed as running; `stop` and `done` of each name again: `unknown_task` naming `start`; `stop` and `done` of an invalid name: `invalid_name`; `list` is empty. (FR-6, FR-7, FR-18, FR-19)
- **AC-10** — `add task-b` with a goal, then `add task-a` from a directory inside the repository with a plan by a relative path, `--priority high`, `--after task-b`, `--waits` and `--until 'test -f released'`: each printed queued with the main working tree, the goal, the plan's absolute path or `null`, the priority or `null`, the waits text or `null`, the added time, `after` and the check as given or `null`; `list` prints `task-b` in `ready` and `task-a` in `waiting`; `add` with a missing plan, an unreadable one and a directory as the plan: `plan_unreadable`; with an `--after` name the store does not hold: `unknown_task` naming `start`; from a path outside git: `not_a_checkout`; with itself as `--after`, with `--priority top`, and with `--until ""`: exit 2 with `bad_arguments`; the queue holds the two tasks only. (FR-8, FR-9, FR-17)
- **AC-11** — `add` of a queued name again with another repository and goal and no priority or waits: the task printed with the new fields and its first added time; `add` of a running name: `name_taken` naming `running`; `add` of an in-review name: `name_taken` naming `review`; `list` prints the running task, the in-review one and the queued one unchanged. (FR-10)
- **AC-12** — A queued task waiting after `task-b` with a waits text and a check: `wait` with `--after task-c`, another text and `--until 'exit 0'` replaces all three; `wait` with none of the three clears all three; `wait --waits` on a running task sets its text and `list --full` prints it; `wait --after`, and `wait --until`, on a running task: `wrong_state`; `wait` of a name the store does not hold: `unknown_task`. (FR-15)
- **AC-13** — A queued task with a plan, `--priority urgent`, `--waits`, `--until 'exit 0'`, and `--after` a queued task and a running one: `start` is `blocked` naming both, `done` for each and `wait` for the task, and the task stays in `waiting`; `done` the queued one: `blocked` naming the running one; `done` it too, and `start` with a session: running with its goal, plan, priority, waits and added time kept, the brief and session recorded and no `after` or `until`; `list` prints it in `tasks` and nothing queued. (FR-11, FR-14)
- **AC-14** — Seven queued tasks of each priority and none, two of them waiting, one on text and one after a task: `ready` and `waiting` are each ordered by priority, urgent first and none last, then added time, then name; `done` the task waited after: the waiter is in `ready` with nothing after; `add` that name again: the waiter is in `waiting` after it again. (FR-14, FR-17)
- **AC-15** — `review` a running task: printed in review with its review time and the rest as it was, and `list` prints it in `tasks` with `briefChanged`; `review` it again: `wrong_state` naming `review`, `wait`, `stop` and `done`; `review` a queued task: `wrong_state`; `review` a name the store does not hold: `unknown_task`; `start` of the name in review: `name_taken` naming `review`; `wait --waits` on it: printed in review with the text; `stop` it: queued with its goal, plan, priority, waits and added time and no review time; `start` and `review` it again, then `done`: printed in review, and `list` is empty. (FR-7, FR-13, FR-15, FR-16, FR-17, FR-18, FR-19)
- **AC-16** — A store whose schema version agent-task cannot read: `list` refuses `store_version`, and the file is unchanged. (FR-4)
- **AC-17** — A version-1 store holding two running tasks, one started before the other, a done task with a commit and a dropped one, one running brief amended since: `list --full` prints the two running tasks oldest first with their added time equal to their start time, no session, goal, plan, priority or waits and the amended brief flagged, and `ready` and `waiting` empty; the store is at this version with the tasks and after tables only; `start` under the done and the dropped names succeeds, under a migrated running name is `name_taken`, and `review` of a migrated task takes it to review. (FR-5)
- **AC-18** — `--version`, then `--version now`: the version alone on stdout with exit 0 and nothing on stderr, then exit 2 with `wrong_arity` and the usage as the act. (FR-20, FR-22)
- **AC-19** — With a task running, no command prints what `list` prints, exit 0; `--help` lists `add`, `start`, `wait`, `review`, `list`, `stop`, `done` and `doctor` and the `--help` and `--version` flags, exit 0; `--help now`: exit 2 with `wrong_arity` and the usage as the act. (FR-21)
- **AC-20** — An unknown command, and `start` with no `--brief`: exit 2, nothing on stdout, `unknown_command` naming it and `bad_arguments` with the usage as the act; a refusal exits 1. (FR-22)
- **AC-21** — The test environment's `HOME` and XDG directories are scratch directories, not the account's. (NF-1)
- **AC-22** — With only git on `PATH`: `add` with a plan, a priority and a check, `start` with and without `--session`, `wait` with `--after`, `--waits` and a check, `review`, `list` with the check met, `stop` and `done` each succeed, and `doctor` exits 0 with git `ok` naming where it was found and `bash`, `agent-task` and `jq` each `warn` naming the directory searched and the session hook. (NF-3, FR-28)
- **AC-23** — *Retired.*
- **AC-24** — Run the `SessionStart` hook as `hooks.json` registers it, from the plugin `plugin.json` names `cniska-task`, with only a shell, bash, git, `jq` and `agent-task` on `PATH`, with two tasks on briefs under one directory, one running and one in review, the running one's brief amended since: from that directory and from its parent, exit 0 printing the context, the heading and then the output of `list --started` as it prints it, with both tasks and their states, the amended one flagged; from a sibling directory with no brief, from the directory of a removed task's brief, and from a directory that does not exist: exit 0 printing nothing. The hooks file registers the session hook alone, matching the four session sources. (FR-24, FR-25)

## 6. Deliverables

- **D-1** — The `agent-task` CLI, run by Bun from a checkout through `bin/agent-task` and linked onto `PATH` by `mise install` in the primary checkout; and beside it the release binary `scripts/build-compiled.sh` compiles, for darwin-arm64 and linux-x64, shipped by a GitHub release with `install.sh`, by the npm packages and by the `cniska/tap` Homebrew formula. Each tarball and `install.sh` carries a build provenance attestation from `release.yml` at the tag, and the release is published only once every file is attached, so a release with release immutability on keeps the files it published, as [`docs/releasing.md`](docs/releasing.md#what-a-release-guarantees) says.
- **D-2** — `README.md`, `AGENTS.md`, `src/README.md`, `docs/commands.md`, `docs/plugin.md`, `docs/development.md`, `docs/releasing.md`, `CONTRIBUTING.md` and this spec.
- **D-3** — The test suite, run by `bun run check`, and the acceptance suite, run by `bun run acceptance`, whose test names cite the criteria in §5. The acceptance suite drives the CLI, the plugin's hook as its `hooks.json` registers it, the compiled release binary, `install.sh` against a stand-in for the release downloads, and the npm packages through their launcher, from outside.
- **D-4** — The `cniska-task` Claude Code plugin in `plugin/`.

## 7. Constraints (fixed)

- **C-1** — TypeScript on Bun, which mise installs, with SQLite through Bun's own driver and TOON through `@toon-format/toon`.
- **C-2** — git and `/bin/sh`, which runs a queued task's check, are the programs the CLI runs, from a checkout or as the release binary. The npm package's launcher runs `uname`, `readlink`, `dirname` and `sed` before it hands over to the CLI.
- **C-3** — The plugin brings neither Bun nor the CLI. Its hook is shell that runs with a POSIX shell, bash, `jq` and `agent-task` alone, and it reads the store only through the CLI.
